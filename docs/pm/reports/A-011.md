### 2.1 The engine seam (Task 1.5)

`MatchHost::with_mission(world, setup, controllers, mission)` is a peer of
`with_controllers` — the verbatim construction body (slot validation, sort,
one-per-slot assert, interpolator seed, tick-0 checkpoint) with the simulation built
by `Sim::with_mission` instead of `Sim::new`. No refactor of `with_controllers`
(the brief's mandate); the `sim` field stays private; `MissionObjectives` imports
from `pandemonium_sim_api`. Because both constructors share `Sim::build`'s body,
tick-0 state is identical by construction — pinned by the seam test
`with_mission_matches_with_controllers_tick_for_tick` (identical state hashes and
checkpoint trails across 62 frames), and the companion
`with_mission_surfaces_the_objective_resolution_the_plain_host_lacks` proves the
mission actually rides through (the mission host emits
`ObjectiveState { 0, Completed }` + `MatchEnded` where the plain host emits
neither, with the hashes pinned equal).

### 2.2 The mission picker (Task 1)

A `Screen::MissionPicker(MissionPickerState)` sub-screen of New Match, opened by a
new "Missions" row at index 5 (after Back) on the New Match screen. The state
mirrors `NewMatchState`: the mission list cycles by index with the map picker's
exact wrap law (`cycle_mission` ≡ `cycle_map`), the seed field edits in place with
the same cap/randomize laws, and the New Match fields the picker was opened from
ride along so Back/Esc restores them unchanged. Start emits the new
`Effect::StartMission { mission_index, seed }`; the app's `begin_mission` bundles
the mission's map (`ContentTree::bundle`), resolves its objectives
(`ContentTree::mission_objectives(id, HUMAN)` — the first map start's player, slot
0), and builds the host through `App::build_mission_host` → `MatchHost::with_mission`
with the opponent's scripted Alpha controller (ADR-0201 §9: "AI: nothing — the
default plan is the slice's opponent"). A tree with zero missions gates both the
Missions row and the picker's Start to no-ops (the machine never emits a
`StartMission` the app cannot resolve). Restart/Rematch rebuilds the same mission
(the A15 drop+reconstruct shape over the mission dimension); a mission-less start
or a drop clears every mission-scoped field.

### 2.3 The objective HUD (Task 2)

`ui::MissionHud` is the one tracker: the mission's display name plus one
`ObjectiveLine` per objective, built from the *resolved* objective set — the same
`MissionObjectives` the simulation receives, so the line indices are the
`Event::ObjectiveState` indices by construction. The draw loop's event pass (the
same `for event in &outcome.events` that reads `Died` and `CommandRejected`)
consumes `ObjectiveState` after the step and feeds the tracker; the HUD block
renders under the notice lines (`ui::objective_hud_quads`) — a `MISSION <name>`
header plus one line per objective with its state marker (`[ ]` / `[x]` / `[!]`).
A mission-less match carries no tracker, so the existing HUD is unchanged. All
text is ASCII (test-pinned).

### 2.4 The cutscene player (Task 3)

`crates/client/src/cutscene.rs` — the reusable live-state player (ADR-0201 §5
option (i)): a scene eases the camera between two ground anchors at the opening
distance (smoothstep) over the frozen live world while a two-line ASCII caption
(subtitle panel: the mission's display name, the one-line objective summary, the
skip hint) rides over the frame. `begin_mission` opens the Phase 1 scene — a ~6 s
pan from the enemy's start to the player's start — and pauses the host through the
existing `set_paused(true)` path. Any key (Esc included) ends the scene and
unpauses; a scene that runs its duration ends itself the same way. The camera then
rests on the player's start at the opening distance (a readable view whatever
moment the skip landed on). The player never submits commands, never reads sim
internals, and touches no state the hash covers; input routing swallows keyboard
and mouse while a scene runs (clicks do not skip — the brief says any *key*).

### 2.5 The end-screen mission text (Task 4)

When a mission match ends, the end screen's subline carries the mission's display
name (under the VICTORY/DEFEAT headline) and each objective's final state rides as
info rows (objective left, `COMPLETED`/`FAILED`/`PENDING` right — the same block
the Controls screen's binding table uses; the `info_lines` type widened from
`&'static` pairs to borrowed pairs, a superset that keeps every existing call
site compiling unchanged). A mission-less match's end screen is unchanged.

## 6. Deviations and assumptions

- **D-1 — the Missions entry is a sub-screen of New Match (row 5, after Back),
  not a main-menu row.** The brief sanctioned either ("A 'Missions' row (or a
  sub-screen of New Match) opens the picker"); the deciding constraint is the
  *untouchable* A-010 Xvfb evidence script (`tests/xvfb/`, outside this brief's
  touch list), which drives the menus by index: main menu `Down,Down,Enter` must
  reach Controls (row 2) and New Match `Down×3,Enter` must reach Start (row 3).
  Any main-menu insertion breaks c1/c2; any New Match insertion before Back breaks
  c3-c12. The chosen placement keeps every existing row's index and every existing
  behavior — empirically proven by re-running the script (13/13 PASS, §3.2). The
  main menu's New Match / Settings / Controls / Quit rows are byte-identical in
  behavior, and the advanced modes stay directly reachable (ADR-0201 §6: the
  campaign is a menu peer, never a gate).
- **D-2 — the HUD's objective text derives from the resolved objective set, not
  content's `defs` types.** `pandemonium_content`'s `defs` module is private
  (`mod defs;`, no root re-export of `MissionDef`/`ObjectiveParameters`), so the
  client cannot *name* those types — their values are reachable through
  `tree.missions` field access, but the HUD builder needs the variant patterns.
  The resolved vocabulary (`MissionObjectives` et al.) is public in `sim_api`, is
  the brief's own Task 1 resolution path, and makes the HUD's indices the event
  indices by construction. Kind names resolve through the bundle's entity order —
  the exact order the content seam resolved the ids by. Not a contract mismatch
  (§3.1); flagged for the PM as a cross-lane note (§10).
- **D-3 — two existing `ui.rs` count pins adapted, and test fixtures extended.**
  `the_new_match_screen_renders_the_fields...` pinned the New Match screen's button
  count at 5; the Missions row makes it 6 (the pin's intent — "the fields render" —
  is unchanged; the count grows because the screen legitimately grew the brief's
  own row). The shared fixtures gained mechanical lines: `MenuInput` constructions
  add `missions: &[]`/`MISSIONS` (the new field), and the screens test helpers
  `ctx()`/`ctx_prefilled()` add `mission_count` (the new `KeyContext` field). No
  test was removed, no assertion loosened — these are the only existing-test
  edits, all fixture-level, all declared here.
- **D-4 — the pinned toolchain installed in-session.** The container had no
  cargo/rustc; `rustup-init` with the pinned 1.98.1 + rustfmt + clippy (the B-009
  D-3 / B-010 D-1 / B-012 D-1 precedent). Unlike those sessions,
  static.rust-lang.org was reachable, so **the full gate — fmt, clippy, both test
  profiles — ran on the pin itself**, not a stand-in; the toolchain note's fallback
  was not needed. Environment-only; the pin governs.
- **D-5 — the local gate ran with the ALSA environment shim, zero repo changes.**
  The B-010/B-012 D-2 precedent: `apt-get download libasound2-dev` + `dpkg -x`
  into the session workspace, the extracted `libasound.so` symlink replaced with a
  real copy of the system runtime's, `PKG_CONFIG_PATH` for the `alsa-sys` probe
  and `RUSTFLAGS="-L ..."` for rust-lld (which does not read `LIBRARY_PATH`). CI
  installs `libasound2-dev` properly; nothing here touches a repo file.
- **D-6 — the cutscene's skip is keys-only; mouse input during a scene is
  swallowed.** The brief: "any key or Esc ends the scene and unpauses". Clicks
  neither skip nor order (nothing may reach a paused host); the wheel does not
  zoom (the scene drives the camera).
- **D-7 — mission semantics decisions, all deterministic and documented in the

## 8. Risks and surprises

- **The `defs` visibility surprise (D-2)** is the session's one genuine discovery:
  the brief's CONTRACT lists the content def types, and they are `pub` — but the
  module is private with no root re-export, so they are unnameable from the client
  crate. The resolved-form path solved it without touching Lane B's files; the
  one-line `pub use` that would make the defs ergonomic is the PM's to route (§10).
- **The optional objective completes at tick 1 on the current content** — the
  Legion's starting force is exactly four workers, and `crossroads_01`'s optional
  objective is "train four workers", so it resolves on the first evaluated tick
  (pinned by `a_mission_matchs_objective_events_feed_the_tracker`, which turns it
  into deterministic evidence). This is authored-content semantics (B-012's D-7(b)
  degenerate-completion case), not a client bug — but the owner may want the
  authored count above the starting force, or a different kind, for a *felt*
  objective. Content is out of this brief's lane; noted for the PM.
- **The repo token transited the chat.** Standing note from every report since
  B-002: rotate it after merge (§11).
- **Look and feel needs owner eyes** (MP-8): the Xvfb drives prove the surfaces
  respond and the state machines are correct; the caption's placement, the pan's
  pacing, and the picker's reading are human judgments.
- **The cutscene + auto-pause interaction is safe by construction** — focus loss
  during a scene finds the host already paused, so `auto_pause_on_focus` no-ops
  (its not-paused guard), and regaining focus never auto-resumes (the classic-RTS
  contract). No new path was needed.
