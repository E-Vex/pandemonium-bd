## Notes and decisions

- **The evaluator is total; content validates.** `survive_status` itself would complete a degenerate 0-window at tick 0 — the loader's 300-tick floor is what makes that shape unloadable (the AUD-003 division, the same one BuildTrain's `count == 0` refusal uses). Likewise `protect_status` is total over the entity set; the starting-forces gate is what keeps a protect objective with nothing to protect from loading. The sim-side unit tests use tight windows (ticks 2-3) because the semantics under test are the boundary tick, not the floor — the floor is pinned where it lives, in the loader tests, and at the authored scale (300) in the acceptance suite.
- **"(from Died events, FD-9)" resolves to the post-cleanup entity set.** Stage 8 removes the dead and fires their outward `Died` events; stage 10 runs after it, so scanning the entity set observes "none remains" on exactly the tick the last one died — the same information the events carry, read where the evaluator lives (inside the tick, on hashed state). Reading the outward event stream mid-tick would invert FD-9's direction (events are consumed after the step); the ADR's own table lists "Died + the entity set" as the expressible basis. The tests pin the causal order in one step's stream: `Died` precedes the failure.
- **The fail-only path needed no redesign.** `ObjectiveStatus::Failed` and the AND-composition's `any_failed → end_match(opponent)` have existed since Phase 1; B-017's protect is the first kind that constructs them. The brief's stop condition ("if the existing objective state machine cannot express fail-only without redesign, stop and report") did not fire.
- **The victory-reachability gate is per-file, the starting-forces gate is tree-level.** The all-Protect check needs only the objective list, so it lives in `parse_mission` (loader.rs, the per-file discipline); the starting-forces check needs the mission's faction, so it lives in `ContentTree::load` beside the faction-reference check (bundle.rs, the cross-file discipline). A mission with no required objectives at all stays legal — the pre-existing all-optional law (it ends only through the elimination rule), unchanged.
- **Domain separation in the mission-id encoding is the kind tag.** Survive is 3, Protect is 4 (appended after Destroy's 1 and BuildTrain's 2), each parameter block encoded in the fixed little-endian discipline behind its tag — the same pattern the capability tags use. No pre-existing objective's byte stream can misparse the new bytes, and a mission carrying neither new kind keeps exactly the id it had before (crossroads_01's pin proves it). The optional fog-preset tail (B-015) is untouched — it still writes nothing for Default, and the new kinds never interact with it.
- **AUD-003, applied to the new kinds.** Survive: the 300-tick floor rejects the vacuous window (0) and the trivial one (under ten seconds of play at the fixed 30 ticks/s) — an impossible window cannot exist (time always passes). Protect: the starting-forces gate rejects the vacuous failure (nothing to protect) and, with the same forces authoring every mission's start, an impossible protection cannot be authored (the kind exists at tick 0 and its survival is in the player's hands).
- **The acceptance probes never touch the frozen tree.** Loader-level acceptance builds in-memory `SourceMap`s over the real content directory (`SourceMap::from_dir(...).mission(...)` — a public, load-bearing seam); the CLI replay probe copies the tree to a scratch directory outside the repository. No file was added under `content/`, `content/factions`, or `content/rules`, and the content hash and map id pins prove the identities unmoved.
