## 1. Summary

The objective vocabulary gains the two Phase 2 kinds that need no new data types
(the planning report's §D Package 3): **Survive** — completes when the match's
tick reaches the authored target (the clock is the input; the world is
irrelevant) — and **Protect** — fails the tick the mission player's last entity
of the protected kind dies, which the AND-composition resolves as the mission
player's defeat (the vocabulary's first *failure* resolution, wired through the
existing `ObjectiveStatus::Failed` and `MatchEnded { winner: opponent }` shape).
Both flow the full pipeline the Phase 1 kinds established: mission file →
schema → defs → loader validation → `mission_data` resolution → sim_api
vocabulary → stage-10 evaluator → outward `ObjectiveState` events → HUD lines.

The mission id's canonical encoding gains the kinds as fixed tags (Survive 3,
Protect 4) with their parameters — identity follows the bytes, so a mission
using them is a different mission; nothing else in any encoder moves. All four
protected baselines re-derived live, bit-identical. No STOP condition fired.

## 2. Changes

- **content/schema.rs** — `RawObjectiveParameters::Survive(RawSurviveParams {
  ticks })` and `Protect(RawProtectParams { kind })`.
- **content/defs.rs** — `ObjectiveKind::Survive | Protect` (+ `as_str`,
  `from_schema`) and the `ObjectiveParameters` variants.
- **content/loader.rs** — the conversion arms: Survive refuses `ticks: 0`
  (R4 — a vacuously complete timer, the AUD-003 lesson); Protect resolves its
  kind against the tree's entities; the unknown-kind error now names all four
  kinds.
- **content/bundle.rs** — (a) `mission_data` resolves the new kinds into the
  sim vocabulary (Protect's kind id through the entity order); (b)
  `encode_mission` gains tags 3/4 with the parameter encodings; (c) **the
  executable AUD-003 check**: a Protect objective naming a kind the mission's
  faction does not *start with* is refused at tree assembly (a target the
  player never fields fails at tick 0 and means nothing).
- **sim_api** — `MissionObjectiveKind::Survive | Protect`,
  `MissionObjectiveParameters::Survive { ticks } | Protect { kind: KindId }`.
- **sim/match_rules.rs** — `survive_status(tick, ticks)` (completes at
  `tick >= ticks`) and `protect_status(world, player, kind)` (Failed when none
  stand, pending while any stand); `objective_status` gains the tick input;
  the `Failed` doc comment's stale "protect, survive" speculation corrected to
  Protect alone (Survive only completes — its failure mode is the elimination
  rule, which still governs underneath).
- **client/ui.rs** — the HUD lines: "Survive N seconds" for whole-second
  targets (ticks otherwise — the HUD speaks player time; the authored unit
  stays ticks), "Protect your Command Center".

## 5. FD compliance

- **FD-4:** the kinds are data selecting code evaluators (one function arm per
  kind); evaluation stays code; no logic in the file.
- **FD-5:** ticks and kind ids — integers only.
- **FD-6:** the kinds cross into the sim through `mission_data` as the
  resolved vocabulary; the sim never sees a spelling.
- **FD-9:** resolutions surface as outward `ObjectiveState` events consumed
  after the step, exactly the Phase 1 family.
- **FD-10:** the vocabulary grows forward-only within the mission schema — an
  older loader refuses the new spellings *loudly* (the unknown-kind error,
  never a silent map), which is the letter of "content never loads through a
  loader older than its schema". The schema version stays 2: the file *shape*
  is unchanged (the kinds are values of the existing parameters enum, the
  entity-capability precedent — the full Alpha vocabulary shipped within
  entity schema v1). Recorded as the package's one design note.

## 6. Deviations, risks, notes

- **The `Failed` doc comment's stale speculation corrected:** Phase 1's
  comment claimed "the Phase 2 kinds (protect, survive)" would produce
  failures; only Protect does (a Survive timer only completes — its failure
  mode is the elimination rule, which still governs underneath, exactly as
  the ADR's AND-composition describes). The comment now says so.
- **A Protect objective never *completes*** — protection is a standing
  failure condition, pending while the target lives. This matches the ADR's
  failure-path wording and keeps optional Protect failures end-screen-only.
  A "protect for N ticks then complete" composite is authorable as
  Protect + Survive pairs (the AND-composition covers it).
- The HUD's seconds/ticks rendering is presentation-only (ASCII either way);
  the authored and encoded unit stays ticks everywhere (FD-5).
