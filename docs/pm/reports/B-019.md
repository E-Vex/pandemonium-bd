# B-019 — Faction variants, inline overrides (report)

**Branch** `b/B-019-faction-variants` · **Base** master `4c3bbc2` (`4c3bbc2a8aa0a49c05b2636be48a0639fec9c591` — master after B-018 plus the client visuals PR #39, verified against `origin/master` before the first commit; no other agent moved it) · **Commits** 4 · **Status**: done, all verification green, goldens unmoved.

Implements the B-019 work package of ADR-0201 Phase 2: a mission can restrict or change its faction with inline overrides — no variant faction file ever joins the tree (the owner's binding decision: variants are inline in the mission file). The override block carries a replacement roster (a subset of the base roster) and/or replacement starting forces; the effective faction is resolved once — `effective_faction`, a pure function of `(mission, base)` — and everything downstream reads that one shape: the tree-level gates, the mission-aware bundle's world (roster, production, starting forces baked into the `TrivialWorld`), and the scripted AI's plan (which derives from the faction's production lists — no AI code change, proven at plan level and at 4500-tick acceptance scale). The mission-less path is untouched (FD-1): `Sim::new`, the plain `tree.bundle(map)`, and `ContentBundle::world()` are byte-identical; the sim crate needed nothing (`TrivialWorld::with_roster` has existed since B-016), and `sim_api` needed nothing either — the brief's conditional sim_api touch ("only if MissionData must carry resolved data") did not fire, because the overrides are faction data, not objective data.

## Touch-list deviations

The brief's touch list: `crates/content/src/{schema,defs,loader,bundle}.rs`; `crates/sim_api/src/lib.rs` (only if MissionData must carry resolved data); tests; `docs/pm/reports/B-019.md`. The content crate, the tests, and this report are all touched; `sim_api` is deliberately NOT touched (the condition did not fire — the overrides are faction data baked into the world, not objective data riding `MissionData`, and the sim's objective seam resolves kinds against the unchanged entity order). Two files outside the list were touched, both reported with their reasons:

- **`crates/tools/src/verify.rs`** — `resolve_replay_verification`'s mission-bearing arm now resolves the world through `tree.bundle_for_mission(&def.id)` instead of `tree.bundle(&def.map).world()`. One semantic line plus its comment. This is work item 2's other half: a mission-carrying replay must re-simulate on the world the recording ran, and for an override mission that world is the effective one — without this change the CLI verifier would compare an effective-world recording against the base world and refuse every override-mission replay (proven in the negative control below). A mission without overrides resolves the base faction and the plain bundle world — byte-identical to before.
- **`crates/client/src/app/mod.rs`** — `begin_mission`'s bundle construction moves to `bundle_for_mission` the same way. One semantic line plus its comment. Without it, an override mission would start a client match on the base world: the restriction would exist in the loader and never reach a real match. `build_mission_host` needed nothing (it reads the bundle it is handed); `begin_match` (the mission-less path) needed nothing and was not touched.

No file under `content/` changed: no file was added under `content/factions` or `content/rules` (the frozen-tree law — the variants are inline in mission files), no mission file was added to `content/missions` (all probes build in-memory `SourceMap`s over the real content, and the CLI replay probe copies the tree to a scratch directory outside the repository). `crossroads_01.ron` is untouched — the identity guarantee, pinned by its standing test.

## Notes and decisions

- **The effective production filters producers as well as producibles.** "Base production filtered to the effective roster" is applied to both sides of the `(producer, list)` pairs: a producer outside the effective roster drops with its list. The reason is the faction-file invariant the effective faction must mirror — `validate_faction` refuses a faction file whose production lists a producer outside its roster, so an effective faction that kept such an entry would be a shape no faction FILE could ever produce, and the AI's plan (which reads the production keys to find its barracks and command center) would keep planning builds the Build gate refuses. The documented consequence: a producer excluded from the effective roster but standing in the starting forces trains nothing — the same consequence a variant faction file would have, and the loader's satisfiability gate refuses any BuildTrain objective that would depend on it (the standing-producer case is pinned in `a_build_train_objective_must_be_satisfiable_under_the_effective_faction`). The stop condition did not fire.
- **Starting forces are deliberately NOT required to be a subset of the effective roster.** The brief's own asymmetry: the roster "must be a subset of it", the starting forces need only "exist in content". A turret that stands but cannot be rebuilt (in the forces, out of the roster) is the "pre-built defense" mission shape this buys; the Protect gate reads the effective forces, so the shape's objectives are still gated. The base faction FILE keeps its own stricter law (forces ⊆ roster) untouched.
- **The mission-aware bundle keeps the tree's canonical identity.** `bundle_for_mission` swaps the faction in place and deliberately does NOT recompute `content_hash`/`map_id`: the content hash golden names the tree's content, and the overrides are mission data whose identity rides the mission id on recordings that carry one (AUD-002) — exactly the B-016 doctrine for the roster field. The world's fixture hash still sees the effective production and starting forces (it always hashed those fields), so an override mission's recording is a distinct match identity — and the CLI verifier resolves the world through the same mission-aware path, so the pair (fixture hash, mission id) reproduces. Pinned in `bundle_for_mission_bakes_the_effective_faction_into_the_world` and `a_restricted_mission_replay_roundtrips`.
- **The BuildTrain satisfiability gate is one level deep, on purpose.** "Targets are in the roster and producible by something in it" is implemented as: the target in the effective roster, and producible by the fieldable set (effective roster ∪ effective starting-force kinds) — a structure needs a Build-capable fieldable kind (the builder the sim's Build command requires), a unit needs a fieldable producer whose effective list trains it (the sim's Train gate's authority). Deeper chains (whether the producer itself can be obtained through further production) are not chased — the brief's parenthetical is one level, and a deeper closure would start rejecting designable missions (e.g. "the first barracks must be built before riflemen exist" is a perfectly legal mid-game objective).
- **The gates run against the effective faction for every mission, override or not.** The effective faction is defined for every mission (base + no-op = base), so the Protect, reach-tick-0, and BuildTrain gates read one shape — the gate's view and the mission-aware world's view run through the same `effective_faction` helper and cannot drift. For a mission without overrides this is behavior-identical to the pre-B-019 gates (the base faction), except the NEW BuildTrain gate, which fires for the first time — crossroads_01 passes it (worker: in the roster, producible by the standing command center).
- **The acceptance probes never touch the frozen tree.** Loader-level acceptance builds in-memory `SourceMap`s over the real content directory; the CLI replay probe copies the tree to a scratch directory outside the repository and adds the probe mission there; the content hash and map id pins prove the identities unmoved. No file was added under `content/`, `content/factions`, or `content/rules`.
- **Environment note (not a code change).** The verification environment ships no `libasound2-dev` (CI installs it); the runtime `libasound.so.2` was present, so the dev package's `.pc` and linker symlink were staged into a local prefix (`PKG_CONFIG_PATH` pointed at it) — no build flag, patch, or dependency changed, and CI's own legs are unaffected.

## Open issues

None blocking. Three boundaries, recorded for the owner:

1. **Override starting forces are not placement-validated.** The base faction's forces sit legally on every map (`validate_map_placements`, per map × faction); a mission's replacement forces are not run through the same check — the brief enumerates the loader checks and placement is not among them, and the base validator's ore-reachability and symmetry halves would over-reject designable missions (e.g. asymmetric override forces on a symmetric map — a classic mission shape). If the owner wants the per-force legality half (bounds, buildability, occupancy) for override forces against the mission's map, that is a small follow-up gate in the same file.
2. **BuildTrain counts are not checked against the effective starting forces.** The "N exist" semantics (the owner's AUD-003 ruling, crossroads_01's comment) means a count at or below the standing count completes vacuously — today that sits on the authoring duty crossroads_01's comment names ("the target must exceed the starting four"). The vacuous-completion guard could be extended to counts when the owner wants it; the brief's parenthetical named roster membership and producibility, which is what this brief implements.
3. **Destroy's satisfiability is not gated.** A forces override that leaves the opponent (the same faction on this content) without structures would make a required Destroy complete through the elimination rule at tick 0. The brief's satisfiability list covers BuildTrain and Protect; Destroy's enemy-side analysis is a different gate with its own design questions (the override applies to the mission faction, which on the Alpha fields both slots).

The scripted AI's depot choice scans entity kinds by capability shape rather than the roster, so a mission excluding the supply_depot would see the AI order Build depot commands that the gate rejects (no state, no crash — the script's self-healing). The acceptance's restriction keeps the depot in; the AI plan tuning overrides (B-021, always last) are the owner's surface for that residual.
