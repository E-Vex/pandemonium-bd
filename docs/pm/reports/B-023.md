# B-023 — Content validation hardening (report)

**Branch** `b/B-023-content-validation` · **Base** master `1c99fec` (`1c99fec2…`, B-022's merge, verified against `origin/master` before the first commit) · **Status**: done, all verification green, goldens unmoved.

B-022's finding 3, closed: the content pipeline's unbounded RON integers and their plain-i32 boundary math. Footprint dimensions, starting-force offsets, and reach-area fields carried no magnitude gates, and the far-edge sums mixed `u32` extents with `i32` tiles in plain `i32` — so a hand-authored entity could crash the loader (debug overflow panic), abort the process (~34 GiB footprint-claim allocation in release), or silently mis-validate (a `w as i32` that goes negative makes every bounds check pass). None of the fixes touches the simulation, the content files, or an in-range authoring path; the goldens are bit-identical throughout.

## The three defects

### 1. Footprint dimensions were unbounded (`validate_entity`)

`Footprint { w, h }` (`u32`) was checked only against zero. A `Footprint(( w: 4294967295, h: 1 ))` passed every check through `w as i32 == -1` — the ore-node bounds sum `node.x + w as i32` went negative and the comparison silently passed — and the tree loaded, the world seam built the spawn, and `Sim::new`'s footprint claim pre-allocated `w * h` tile entries (~34 GiB, release abort). A `w` near `i32::MAX` instead overflowed the validator's own far-edge sum (debug panic; release wrap to a negative "far edge" that also passes). The file-level gate now refuses any dimension beyond `MAX_MAP_DIMENSION` (4096) with `InvalidStat` naming field and value — a footprint wider or taller than the largest accepted map can never be placed on any loadable map, so the rejection is precise, not a trade.

### 2. Starting-force offsets were unbounded (`validate_faction`)

`offset: (i32, i32)` fed `anchor + offset` in plain i32 at three sites (the placement validator, the reachability seeder, the world seam) — an `i32::MAX` offset overflowed in debug and wrapped in release. The file-level gate now refuses any component with magnitude ≥ `MAX_MAP_DIMENSION` (4096): anchors are `0..dimension-1`, so ±4095 is the most any map could ever absorb, and ±4096 can never land inside any loadable map. Per-map precision stays with the placement validator (its `IllegalStart` errors name the real map); the edge is pinned — offset 4095 still dies at placement with the exact 16×16 bounds error.

### 3. Reach-area magnitudes were unbounded at file level (the loader's area conversion)

Rect `w/h` (`u32`) and circle `cx/cy/radius` (`i32`) had only B-018's degenerate-shape gates at file level; absurd magnitudes passed file validation and died only at the tree-level bounds gate — which has been i64-total since B-018, so nothing crashed, but the early error did not name the mission file, and the rect's `u32` extents flowed into tree-level i64 math ungated. The file-level conversion now refuses the never-loadable-anywhere envelope derived from `MAX_MAP_DIMENSION`: rect extents beyond 4096, a circle radius beyond the largest map's half-extent (2_048_000 milli-tiles), and a circle center outside `0..4_096_000` milli-tiles. The per-map bounds and whole-map-coverage gates stay tree-level (B-018's), where the error names the real map.

### The boundary math itself (defense in depth, all three defects)

The ore-node bounds and interval-overlap comparisons in `validate_map_file` now run in i64 — total over every `u32`/`i32` pair, independent of the file-level gates (a future caller that bypasses the loader cannot reopen the hole). The world seam's `tile_center` widens its milli-tile product to i64 with a monotone clamp into `from_milli`'s `i32` domain (identical values for every validated input).

## Risks and surprises

- The seam-level test's first draft tripped over a real interaction: a huge footprint overlaps every other ore node, so the overlap rejection fires before the bounds sum. The committed test makes the monster the map's only ore node — worth knowing if someone extends that test later.
- The old-code proof (`git stash` of the base `validate.rs`/`loader.rs`) confirmed the silent pass exactly as B-022 described it — `unwrap_err()` on `Ok` for the `u32::MAX` shape. The `i32::MAX` debug-overflow shape is the same sum one operand apart; the committed gate closes both.
