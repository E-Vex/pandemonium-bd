### 1.1 New golden-preserving candidates derived from the code this session

These are new proposals under BRIEF B-006 item 1 ("implement only proposals you can
argue preserve the exact output"), derived from reading `nav.rs`, `movement.rs`,
`world.rs`:

- **P-A — A\* scratch reuse.** `NavGrid::find_path` allocates three flat O(map) arrays
  fresh on every call — `g_score: vec![i64::MAX; tiles]` (8 B/tile), `came_from:
  vec![u32::MAX; tiles]` (4 B/tile), `closed: vec![false; tiles]` (1 B/tile) — plus a
  fresh `BinaryHeap`. On the 128×128 proving ground that is ~212 KB of allocation and
  fill per request, and the tick-0 storm issues ~1820 requests inside one tick. A
  persistent scratch (arrays + heap kept across calls, reset by a touched-index list)
  restores the exact initial values on exactly the entries a search dirtied, so every
  read sees the same values in the same order: the expanded sequence, the heap's push/
  pop sequence, and the returned path are bit-identical by construction. Untouched
  entries were never dirtied, so they still hold their initial values — the arrays are
  semantically equal to fresh ones at every read the search performs.
- **P-2 — push-apart flat reused cells + precomputed store indices** (the proposal-2
  variant above). Same cell assignment, same ascending-id cell lists, same 9-offset
  scan order, same `a < b` pair law, same arithmetic — but the cell grid is a reused
  flat buffer (no per-tick 393 KB zero-fill, no per-cell Vec allocation churn) and the
  pair loop reads entities/movement through indices computed once at stage entry
  (the stores do not gain or lose entries inside stage 6 — no spawns or deaths run
  between the index build and the last pair), replacing 4 binary searches per
  candidate pair with O(1) indexed reads.
- **P-3 — steady-state lookup trims in the movement/economy per-entity chains**
  (request_paths' travel-target chain, steer, detect_stuck) — same pattern, smaller
  constants. Only if the measured profile ranks it material after P-A/P-2/P-1.

**Ranking is finalized only after the baseline and a sub-stage profile are measured**
(this report, §2 and §3) — the brief's order is ranked-by-gain/risk, and the gain
numbers must come from this host, not from B-002's shares.

### 2.1 The differential mode (instrument, committed before any sim change)

`tools diff-check` (commit `c197216`, tools crate only — the brief's differential
mode): runs N seeded AI-vs-AI matches over the real content (the flagship
configuration's shape; both slots scripted controllers through the engine's
`AiMatchHost`), collects each match's full checkpoint hash trail (tick 0 + every
`CHECKPOINT_INTERVAL` boundary + the forced final), and prints ONE digest line
per seed — `XxHash64` over (seed, checkpoint count, every (tick, hash) in trail
order). Any state divergence at any checkpoint moves that seed's line even when
the final hash cancels out. A `--scale N` tier digests the proving-ground
scenario the same way. The mode is read-only telemetry (it constructs the same
matches `headless` constructs and feeds nothing back); re-runnability is pinned
by a unit test, and both tiers were re-run once locally with EMPTY diffs before
being recorded here.

### 2.6 B-002 proposal 1 STOPPED by measurement (the brief's step-1 rule)

Before implementing, the moved-carrier fraction was measured with scratch
instrumentation (uncommitted, reverted): the incremental-vision gain assumes
most carriers stand still tick-over-tick, so their disks can be skipped.
Measured at scale 10x (per 500-tick window): **94.5 % / 72.3 % / 41.8 % of
carriers move every tick** (the tick-0 storm jostles nearly everything; the
steady crowd keeps 42-72 % moving). A moved carrier costs TWO disk walks
(unmark old, mark new) where the batch scheme pays one — so the incremental
scheme is neutral-to-worse at 10x on this workload (window 1: ~1.9x the batch
disk cost; window 3: ~0.84x — a 16 % best-case saving on a 6 % stage). At
Alpha scale the fraction is 12-17 %, but Vision there is tens of µs inside a
247 µs avg that already meets its §15 budget with 4x headroom. The B-002
SAFETY label was re-derived as correct (the fog-bit-identity algebra in §1);
the GAIN is disproven by measurement. **Proposal 1 is stopped, not implemented**
— the report records this as a B-002 label whose gain half proved wrong (the
brief's STOP rule for a wrong label is scoped to a label that lets a golden
move; this one only misplaced the win, so the remaining proposals proceed).

What survives for vision is the batch walk's per-tile arithmetic (a
constructed-`Vec2Fx` tile center and a full `len_sq_raw` per tile —
bit-identical to rewrite as two integer multiply-compares), re-ranked below
the movement-side work where the measured money is.

### 3.1 Commit — P-A' "the A\* inner-loop package" (nav.rs)

**The change** (crates/sim/src/nav.rs only):

1. `NavGrid` gains a fused `walkable: Vec<bool>` — exactly
   `passable[i] != 0 && occupied[i] == 0` — maintained at the only three
   mutation points (`new`, `occupy`, `vacate`). `passable()` reads one array
   instead of two; `is_occupied` keeps reading `occupied` (different question).
2. The A\* pop loop hoists the loop state (width/height locals, the walkable
   slice) and replaces the per-neighbor `passable()` calls with inline
   ok-x/ok-y bounds tests (exactly the in-bounds halves of the old checks —
   the popped tile's x/y are in-grid by construction) plus single loads of
   `walkable`. The corner-cut companions read `walkable` the same way.
3. The open heap is pre-sized (`tiles/8`, min 64) — capacity never affects a
   binary heap's ordering, so the push/pop sequence is unchanged.

**The bit-identity argument:** `walkable` is a pure function of the two arrays
it fuses, recomputed at every place either component changes, so `passable()`
returns the same bool for every (x, y) as before; the neighbor loop's explicit
bounds tests accept exactly the (dx, dy) offsets whose `nx`/`ny` passed the old
method's bounds check; every skip, relaxation, heap push, and pop sees the same
values in the same order — the expanded sequence and the returned path are
bit-identical by construction. (Considered and rejected: u128-packed heap keys
— ~7 % for a new overflow surface; a bucket priority queue — the
within-plateau ordering risk is exactly the bug class the differential exists
to catch, and even a 3× A\* win cannot reach the 8 ms row, see §4.)

- Goldens: demo `0xb6fff6659cfb7709`, flagship `0x6e9a18bd7c5f699f`, scale-10
  scenario `0x11bf5135d865e045` — all bit-identical to master.
- Differential: AI tier 200 seeds × 4500 ticks — **empty diff** vs baseline;
  scale-10 tier 6 seeds × 1500 ticks — **empty diff**.
- Gate: fmt OK; clippy `-D warnings` OK; **576 dev / 571 release** (master's

### 3.3 Commit — P-2 "flat push-apart cells + indexed pair resolution" (movement.rs)

**The change** (crates/sim/src/movement.rs, `push_apart`/`resolve_pair` only):

1. The per-tick cell grid is a flat counting-sorted pair — a `starts` offset
   array over cells plus a `placed` ordinal array — instead of
   `vec![Vec::new>; cells]` (a ~393 KB outer zero-fill plus a heap allocation
   for every non-empty cell's first push, every tick, before any pair is
   examined). Counting sort is stable over the ascending-id collection order,
   so cell membership AND within-cell order are identical.
2. Each mover carries its entity-store and movement-store indices
   (`MoverSlot`), computed once at stage entry; `resolve_pair` reads records
   by index instead of four binary searches per candidate pair (~11.7 K
   candidate pairs per tick at 10x paid ~44 K searches before). The stores
   gain/lose no entries inside stage 6 (spawns are stage 3, removals stage 8),
   so the indexed reads are the same records the lookups returned.

**The bit-identity argument:** same unit set in the same order (one pass over
the entity store, one movement-store probe per entity — the probe the old
`move_of` filter performed); same cell assignment arithmetic; same 9-offset
scan; same `a < b` id law; same per-pair reads (by the indices the lookups
would have returned) and same writes. Every pair is visited in the same order
with the same arithmetic.

**Evidence (this host, release):**

- Goldens: demo, flagship, scale-10 scenario — bit-identical (values in §3.1).

## Annex E — The remaining gap and what each further step would need

**The final state: 26.20 ms avg at 10x against the ≤ 8 ms row — 3.3x over,
with the golden-preserving proposals exhausted.** The measured split on the
final head: Movement 24.25 ms (92.6 %), of which ~23 ms is A\* search time
(~21 K full-grid searches per 1 500-tick run at ~1.1–1.2 ms each after P-A');
Vision 1.36 ms; Economy 0.21 ms; Combat 0.34 ms; everything else < 0.1 ms.

Why nothing golden-preserving remains:

- **The search count is semantics.** The scenario scripts two ~1 820-request
  waves (ticks 0 and 150 — the re-gather wave replaces every Gather order,
  clearing every path), and the crowd-stuck machinery generates ~17 K more
  repaths (STUCK_TICKS = 30, MAX_REPATHS = 4: the crowded workers burn their
  budgets mostly in the first 500 ticks). Every one of those searches is
  hashed-state-driven; deferring or skipping any moves the goldens.
- **The per-search scope is semantics.** Gather/deposit targets are entity
  centers standing on their own footprints — the goal tile is blocked, `found`
  can never fire, and the search exhausts the open set before selecting
  `best_tile`. Early-exit proofs do not exist for the (h, index)-argmin over
  the reachable set (a closer tile can always appear later in pop order), so
  the full-grid exploration is required by the current result definition.
- **The per-search cost is now machinery-bound.** ~17.4 K pops × (heap sift +
  L2-resident 131 KB g\_score traffic + the filter chain). The remaining
  bit-identical levers were considered and rejected with reasons (§3.1: u128
  key packing ~7 % for a new overflow surface; bucket priority queue —
  within-plateau ordering risk).

What each golden-moving lever would need (none implemented on this branch):

| lever | what it buys (estimate) | authorization it needs |
|---|---|---|
| Path-request budgeting (B-002 #3) | the tick-0/150 storms amortize from ~6.4 s to ~ms; p99/max collapse | standing orders §7 golden-move commit + a semantics review of the deferral order (which requests run first) |
| Crowd-aware gather assignment (B-002 #4) | removes most of the ~17 K repath churn and the crowding feeding it | §7 golden-move commit + gameplay review (worker spread changes match shape) |
