## 1. Summary

ADR-0201 §3's flagged asymmetry is closed: the `Build` validation arm gains the roster
membership check the `Train` arm always had (`producible_by`) — a Build for a structure
the faction's roster does not carry is refused with `RejectReason::InvalidTarget`,
before the economy and placement checks, so a restricted roster is *authoritative*,
not merely a hidden UI button. `TrivialWorld` gains the `roster: Vec<KindId>` field
(the planning report's B2 option (a)), baked from the faction by
`ContentBundle::world()` through the same seam the production lists already ride
(FD-6); the field is deliberately **not** part of `TrivialWorld::content_hash`
(the report's R9 — the content golden is the bundle's hash over the faction bytes;
restriction identity is the mission id's job).

All four protected baselines re-derived live and bit-identical: content
`0x9bc18c521107b262`, map `0xd38136401ab02ff1`, demo `0xb6fff6659cfb7709`, flagship
`0x6e9a18bd7c5f699f`. No STOP condition fired.

## 5. FD compliance

- **FD-2:** the check is inside the existing validation gate — one more
  `RejectReason`, no new mutator, no new command path.
- **FD-4:** the roster is data (the faction file's list) selecting what the code
  gate accepts — exactly the "restrictions are authoritative" ruling; add-a-file
  discipline unchanged (a new faction file's roster reaches the gate through the
  same seam with zero engine changes).
- **FD-5:** `Vec<KindId>` — integers.
- **FD-6:** the roster reaches the sim through the world seam only; the sim never
  reads a faction file.

## 6. Deviations, risks, notes

- **R5 materialized as a fixture issue, not a content issue:** no real-content
  Build command was ever off-roster (the Legion fields every structure it can
  build); the only casualty was the A11 pinned test's use of `ore_node` as a
  convenient 2x2 structure — now correctly refused (a neutral node is not
  faction-buildable, which is the gate's own semantics). The test was re-authored
  around `supply_depot` with identical assertions; the fuzz arms that build
  arbitrary kind ids still pass (off-roster kinds reject identically under every
  controller labeling — the A11 property holds).
- **The fixture-hash non-encoding (R9) is load-bearing:** encoding `roster` into
  `TrivialWorld::content_hash` would have moved every replay-recorded fixture
  identity for zero value (the data is the faction's bytes, already covered by the
  bundle hash on the real-content path; on the mission path the restriction rides
  the mission id). Recorded in the field's doc comment.
- The `roster: Vec::new()` defaults in Build-less test fixtures are inert (the
  gate never runs for them); the two Build-issuing fixtures carry real rosters.
