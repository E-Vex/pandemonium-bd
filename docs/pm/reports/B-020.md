# B-020 — Rules variants (inline overrides) (report)

**Branch** `b/B-020-rules-variants` · **Base** master `35d901b` (`35d901b04b9777f95ca9cb1d3733c9289e26494d`, master after B-019, verified against `origin/master` before the first commit) · **Status**: done, all verification green, goldens unmoved.

Implements the B-020 work package of ADR-0201 Phase 2: a mission can override plain integer fields of its ruleset inline — the starting ore balance and the base population cap — with no variant rules file added to the tree. The override block carries `starting_ore` and/or `base_population_cap`, each individually optional; the effective ruleset is resolved once — `effective_rules`, a pure function of `(mission, base)` — and everything downstream reads that one shape: the tree-level gates (Gather amount vs. effective starting ore; BuildTrain counts vs. effective forces and population cap), and the mission-aware bundle's world (resources starting balance and base population cap baked into the `TrivialWorld`). The mission-less path is untouched (FD-1).

## Rules fields and how the sim reads them (work item 1)

`content/rules/alpha.ron` declares the following fields. Only the two plain-integer fields marked below are overridable; every other field is reported here and is not implemented (the brief's stop condition: an override touching a non-integer or unlisted field is forbidden).

| Field | Type | How the sim reads it | Overridable |
| --- | --- | --- | --- |
| `schema_version` | u32 | Loader version gate only; never reaches the sim. | no (version, not a sim value) |
| `id` | String | Ruleset identity; a mission's `rules` reference is validated against it. Not a sim value. | no (identity, not a plain integer) |
| `display_name` | String | Human-facing only; never reaches the sim. | no (string) |
| `resources[].id` | String | Resource registry id; `world()` maps ids to `ResourceId` indices in ledger order. | no (identity) |
| `resources[].display_name` | String | Human-facing only. | no (string) |
| `resources[].starting` | i64 | **Plain integer.** `world()` copies it into `TrivialWorld.resources[].starting`, which becomes every player's ledger starting balance at tick 0. | **yes — `starting_ore`** |
| `base_population_cap` | u32 | **Plain integer.** `world()` copies it into `TrivialWorld.base_population_cap`, used by `production::population_cap` for headroom. | **yes — `base_population_cap`** |
| `victory.kind` | String | Selects the victory condition code path (`"elimination"`). | no (string, selects code) |
| `victory.allow_resignation` | bool | Match condition parameter; not a plain integer. | no (bool) |
| `file` | String | Source path, carried for errors/tools only. | no (not content) |

No other fields exist in the Alpha ruleset, so the override surface is exactly the two plain integers above. Any future non-integer field is deliberately out of scope and would be a separate work package.

## Changes

- `crates/content/src/schema.rs` — `RawMission` gains the optional `rules_overrides: RawRulesOverrides` field (`#[serde(default)]`, deny-unknown-fields); `RawRulesOverrides` mirrors the two optional sub-fields (`starting_ore: Option<i64>`, `base_population_cap: Option<u32>`).
- `crates/content/src/defs.rs` — `RulesOverridesDef` (canonical mirror) and the `rules_overrides: Option<RulesOverridesDef>` field on `MissionDef`.
- `crates/content/src/loader.rs` — parses the block, file-level no-op normalization to `None` (absent/empty/all-`None` are one shape and one mission id).
- `crates/content/src/bundle.rs`:
  - `effective_rules(mission, base)` — pure resolution, base ruleset with overrides applied in place (ore resource starting balance, base population cap); base ruleset unchanged when no overrides.
  - `bundle_for_mission` now also resolves `bundle.rules` through `effective_rules`, so the world's ledger (tick 0) and population cap carry the overrides. The shared `ContentTree` is never mutated; canonical `content_hash`/`map_id` stay the tree's (B-019 doctrine).
  - `encode_mission` gains a rules-overrides tail behind its own domain tag `RULES_OVERRIDES_ENCODING_TAG = 0xF2`, presence flags per sub-field, encoding only when the block actually overrides something.
  - Tree-level gates: the Gather amount floor reads the effective starting ore; the BuildTrain satisfiability gate gains the count guards — a count at or below the effective starting count is refused (vacuous completion), and a unit count whose population cost exceeds the effective population cap (base cap plus the population provided by the effective starting structures) is refused. Population-cap check is skipped when the effective cap is zero so that the existing no-depot fixture shapes remain legal.
- `crates/sim_api/src/lib.rs` — untouched (overrides are rules data baked into the world, not mission-objective data riding `MissionData`).
- `crates/sim` — untouched (reads `TrivialWorld.resources` and `TrivialWorld.base_population_cap` as before; effective values arrive through the bundle).

## Open issues

None blocking. One boundary recorded for the owner: the BuildTrain population-cap fit check is a static, one-level statement (`count * population_cost <= effective cap`). It cannot know which supply depots a mission will build mid-match, so a mission whose count needs depot construction to raise the cap is accepted only when the base cap (plus starting structures) already covers it; deeper reachability is left to play, matching the B-019 one-level satisfiability doctrine.
