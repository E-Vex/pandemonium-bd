## The three defects

### 1. Finding 5 — the soak's telemetry hardcoded slots 0/1 (`soak.rs`)

`record_outcome` matched `Some(PlayerId(0))` and `Some(PlayerId(1))` explicitly; every other id fell into the `Some(_)` arm and was counted as **mutual destruction**. A map with starts `[2, 3]` reported every decisive win as mutual destruction, and `outcome_label` / the summary line named players 0/1 regardless of the map. The sweep now derives the driven players from `bundle.map.starts` and keys everything on them: `SoakReport` carries the `players` beside the wins (index `i` of `wins` is the `i`-th start's player), `record_outcome` matches the winner against them (`NEUTRAL` and any id outside the starts — unreachable from a real match, where stage 10 crowns a setup player or `NEUTRAL` — keep the no-winner arm), the verbose label names the winner's real id, and `print_report` prints the actual players. The repo's content starts 0/1, so no recorded evidence changes — the 2-match live smoke prints the same line it always printed.

### 2. Finding 6 — `bench --ticks`/`--scale` preallocated unchecked (`bench.rs:143`, `scale.rs:144-146`; plus the same shape at `diff_check.rs:103/133`)

`Vec::with_capacity` received the raw CLI counts. **Proven live at the base**: `bench --scale 4294967295` aborts the process — `memory allocation of 13743895360160 bytes failed`, exit 134 — instead of printing a usage error. Every count that feeds an unchecked preallocation in this crate is now range-validated at the clap boundary: `bench --ticks` 1..=36000, `bench --scale` and `diff-check --scale` 1..=10 (the shared `scale::MAX_SCALE`), `diff-check --matches` 1..=1000. Every cap derives from the project's own documented vocabulary (A-209's law, the A-208 pattern applied to CLI counts) — plan §15's tier ladder tops at the 10× row and the proving ground's authored 1000-per-side forces saturate there; A7 calls a match stuck past 20 minutes of game time (36 000 ticks at 30 Hz, the soak's own default budget); A7's 1000-match sweep is the largest the nightly's sharding vocabulary defines. Two strictness trades, both recorded in A-209 for the owner: zero is refused everywhere (a bench that samples nothing, a sweep that checks nothing), where `--scale 0` previously aliased *silently* to scale 1 through `scaled_world`'s `scale.max(1)`; and values above the caps are refused where they previously produced runs identical to the cap (only the preallocation kept growing).

### 3. Finding 7 — `replay-verify` demanded a content directory even for demo records (`main.rs:218`)

The arm resolved the content directory **before reading the record**, so a stripped install (the binary and a demo replay, no `content/` anywhere in the search) failed with `content directory not found` before decoding — though a demo-world record carries the demo's own identity and needs nothing from disk. **Proven live** (two debug binaries built in throwaway worktrees, the worktrees then hidden so each binary's compiled-in dev path dies, CWD a directory with no content): the base binary fails with exactly the finding's error; the branch's binary answers `replay-verify: PASS — 3 checkpoints reproduced`. The resolution is now lazy through a resolver closure — `resolve_replay_verification` takes the search itself, so the law lives in one place: a mission-less demo-world record (the `is_demo_record` identity pair, extracted beside `resolve_replay_world`) takes the in-code demo world and an empty mission set without consulting the resolver at all; every other record (a content-world record, or a mission-bearing one) resolves exactly as before, and a failed search still fails with the search's own error naming every path it tried — also proven live: the content-world record from the same stripped directory still fails with `content directory not found. Searched: …`.
