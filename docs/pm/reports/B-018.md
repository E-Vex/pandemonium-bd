## Notes and decisions

- **The ledger does not record cumulative delivered ore — the events do.** The brief's instruction ("first check whether the ledger already records it") resolves to: the ledger holds only current balances (`PlayerState.resources`); spending breaks any derivation of cumulative totals from balances, and node depletion breaks any derivation from node bodies (cargo in transit). The ADR's own §2 table names the expressible basis: "cumulative `ResourceDelivered` (`economy.rs:156`)" — so the evaluator derives the total from the delivery events, exactly as directed. The stop condition did not fire.
- **The attribution field is the design decision of this brief.** A cumulative total is per-player (the mission player's), but `ResourceDelivered` carried only the worker id, and a worker that delivers at stage 4 can die at stage 8 — unresolvable at stage 10 by any in-tick lookup. Extending the event with `owner` (the credited ledger, resolved at deposit time, where the credit itself already computed it) makes the attribution exact and structural: immune to same-tick deaths, carried on an outward, unhashed, non-codec event (no hash, golden, or replay byte can move — pinned by both goldens), and the smallest honest change (the value already existed at the construction site). The alternative — a worker-owner lookup at stage 10 — would silently under-count on the delivery-then-death tick; a persistent id->owner map would be new hashed state. Both rejected.
- **Reading the events at stage 10 is FD-9-compatible in this direction.** The events still flow outward and are consumed after the step (nothing is consumed, nothing flows inward); the evaluator reads what stage 4 produced in the same step, before the step returns them — so a delivery completes its objective on its own tick, with `ResourceDelivered` preceding `ObjectiveState` in the outward stream (the causal-order law, pinned in both the sim unit tests and the real-content acceptance). B-017's protect arm chose the post-cleanup entity set because the set carried the same information as the `Died` events; for gather there is no hashed-state equivalent (balances and node bodies both diverge from delivered totals), which is precisely why the ADR's table routes the kind to the events.
- **The accumulator is derived state, not hashed state.** `MissionState.delivered` is a function of the match inputs (seed + content + command log — FD-1's identity), rebuilt identically in every re-simulation: the lockstep twin tests and the replay round-trip pin the hashes identical while the accumulator grows. The brief's "do not add a field to hashed sim state" holds — the field lives on the unhashed mission state.
- **Coverage before bounds, for circles especially.** A circle containing all four map corners necessarily leaves the map (containing the diagonal needs `2r >= diagonal > min(W, H) >= 2r` in-bounds — a contradiction), so a bounds-first order would report the semantic authoring error ("covers the whole map") as the structural one ("leaves the map"). The rect's coverage check is the spanning form (`x <= 0 && x+w >= width`, and the same in y) so an overspanning rect gets the same semantic message. Documented in `validate_reach_area`.
- **The tick-0 gate and the evaluator share one predicate.** Both call `sim_api::AreaSpec::contains` over the same exact positions (`tile_center`'s arithmetic, footprint from the entity kind, the first start's anchor — the mission player's convention slot, the one every Phase 1/2 caller and `verify.rs`'s re-simulation pass `mission_data`). The gate cannot drift from the evaluation, and the boundary tests at all three levels (geometry, evaluator, loader-against-real-forces) pin the same laws: rect half-open, circle inclusive, `from_milli` truncation documented and sub-milli-tile.
- **The gates scope to the mission player's convention slot, not every start.** An area containing the opponent's starting forces loads — "reach the enemy base" is a real objective, since the objective counts only the mission player's entities. Pinned in `bundle.rs` (`a_reach_area_beside_the_opponents_start_loads`) and exercised end-to-end by the replay probe's rect near the enemy side. A caller that picks a different mission-player slot than the convention owns that deviation (all current callers use the first start's player).
- **AUD-003, applied to the new kinds.** ReachArea: the degenerate shapes are refused at file level, the out-of-map/whole-map shapes at tree level, and the vacuous tick-0 completion through the evaluator's own predicate — an impossible "never enters" cannot be authored on an in-map area that a unit can walk to. Gather: the amount gate (above the effective starting ore, both semantics) refuses the vacuous completion for the balance (starts satisfied) and the near-vacuous one for the cumulative (one trip); the evaluator itself is total (the B-017 survive division — content validates, the evaluator completes whatever it is handed).
- **The acceptance probes never touch the frozen tree.** Loader-level acceptance builds in-memory `SourceMap`s over the real content directory; the CLI replay probe copies the tree to a scratch directory outside the repository and adds the probe mission there; the content hash and map id pins prove the identities unmoved. No file was added under `content/`, `content/factions`, or `content/rules`.
